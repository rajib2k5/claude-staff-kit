- `learn-as-you-build`: a fifth mode, `queued`, for a user who runs several projects or sessions at once, or wants the full quiz without blocking the build. In `full` mode, each session paused at every milestone until the user said "continue", so every build waited on one quiz at a time. In `queued` mode, the session writes the full checkpoint (re-asks, lesson-and-question pairs, 5 to 8 explain-it-back questions) after the commit that finishes the milestone, delivers it, brings the log up to date, and starts the next milestone at once, in the same turn. Several checkpoints can be open at once. An open queued checkpoint is not owed: the log lists it as `queued, N of M answered`, on a new queued list that says how to resume it. An answer line or a results message goes to the checkpoint file of the milestone it names. An answer is recorded with a one-line reply in the widget, or with the explanation of every option in markdown, and the build goes on as it was; results are graded at once, on the strongest model, and only urgent work, or an open question about the pin, delays the grading. In markdown, every unanswered item goes out in one message, a reply that names no item gets `Which item?` before it is recorded, and a reply that names no milestone, while several checkpoints are open, gets `Which milestone?`. The widget's fixed header line, the `Recorded` reply, and a "Grade now?" ask with several checkpoints open name the milestone. Re-asks come from the missed topics in the log when the checkpoint file is written, and a topic that an open checkpoint already re-asks is not chosen again while that re-ask has no answer. A `Code at:` line pins each queued checkpoint to its milestone commit, on a branch that is kept, such as a pushed `main`. With no such commit, the session copies every file that differs from the newest kept commit under the work to `.learning/milestones/NN-code/`, not only the cited ones, and the line names the copies and that commit (`copies in .learning/milestones/NN-code/ on top of <sha>, <date>`). A file that is not in the copies is read from that commit. The line has no period after the sha. The widget header, and each lesson of a checkpoint written in `queued` mode, say that the items describe the code at that commit, its citations are not refreshed, a later milestone does not retire its items, and its explain-it-back answers are graded against that commit, with each `file:line` labelled with the pin. A resume with several open checkpoints lists each one with its N of M, and the build goes on while the session waits for the pick. In `queued` mode, every open checkpoint that is not owed is queued, also one paused in `full` mode or written before the switch. One with no `Code at:` line gets the last commit of its milestone at once, and only a pin in its widget header. If that commit is on no kept branch, the files that differ between it and the newest kept commit under it are copied from it with `git show <sha>:<path>`. If the commit is not clear, the session asks in one line, keeps building, and does not grade that checkpoint until the answer. On a switch to `full`, the next milestone pauses and open queued checkpoints stay queued; on a switch to `lite` or `deferred`, they become owed; on a switch to `off`, they and their log entries stay as they are. A restarted queued checkpoint reads `queued, attempt 2, N of M answered`. The less intrusive order is now `off`, `deferred`, `lite`, `queued`, `full`. The token-economy rule now limits the recording of an answer, not the whole turn, so the work goes on after the reply.

### Fixed
- `evolv-destructive-guard.js` and `pre-publish-guard.js` asked about work that only touches Claude's own files or regenerable output. The guard now treats these as not the user's data:
  - Claude's temp root on Linux: everything inside `<tmp>/claude-<uid>/` (digits only: `claude-backups` is not it), where `<tmp>` is `CLAUDE_CODE_TMPDIR`, else `TMPDIR` (`os.tmpdir()`), else `/tmp`. Deleting the `claude-<uid>` folder itself still asks, and the temp base itself is denied like `/tmp`.
  - A variable assigned a literal once, at the top level of the same command line (`S=<path>; rm -rf $S/x`, also `export`), is judged by that path, also through a chain of such variables (`B=$A/x`), resolved in one pass and never parsed again. It stays unresolved, so the command still asks, when the name is reassigned, set in a loop, a block, a function, a subshell, a pipeline, a backgrounded list, behind `||`, behind `&&` (also across a line break) but used after `;`, from a command substitution, when the value itself holds an expansion that is not resolved, when `IFS` changes, or for names the shell changes itself (`PWD`, `OLDPWD`). Nothing is resolved on a line with `eval`, `source`, `.`, `trap`, a nameref, `exec {VAR}>`, or `read`, `mapfile`, `declare`, `typeset`, `local`, `export`, `readonly`, `printf -v` or `wait -p` given a quoted or indirect name, or whose resolved form has one of them (`X=eval; $X …`). A chain that would grow past 8 times the line (64 KB at most) is not resolved. Values from the real environment are never used. `$PWD` is the working folder only on a line without `cd`, `pushd` or `popd`.
  - Regenerable caches named exactly: `__pycache__`, `.pytest_cache`, `.hypothesis`, `.mypy_cache`, `.ruff_cache` and `node_modules/.cache`, by `rm`, `find -name … -exec rm {} +`, `find -name … -delete` and `find -name … -print0 | xargs -0 rm`. Plain `find … | xargs rm` (names split on spaces), `-fprint`/`-fls` and other find actions, a brace word (`~/dev{,/__pycache__}`), `.venv`, `node_modules`, `.tox`, a glob, a negated or `-o` find, or extra targets still ask.
  - `chmod -R` with an owner-add-only mode of `r`, `w`, `x` and `X` (`u+rwx`, `u+x,u+w`) on project folders. `u+s`/`u+t`, a numeric mode, a group, other or all change, `-` or `=`, `--reference`, `sudo`, `/`, `~`, a system folder, an unresolved target, `chown -R` and (new) `chgrp -R` still ask.
  - Redirections are no longer read as words: `git push 2>&1 | tail -1` was asked as "cannot resolve what this push publishes (main 2> to origin)", and `rm -rf x 2>/dev/null` read `2` as a target. The push is still judged on what it publishes. `>|` to a system file asks like `>`.
- `pre-publish-guard.js` no longer asks about a home-directory path in an untracked file that the commit does not include: a `git add c.txt` earlier on the line used to make the guard read every untracked file, so `git add c.txt && git commit` asked about an unrelated `untracked.log`. The scan is now narrowed to the staged diff plus the added paths only when the raw command matches one exact shape (the grammar is in the `NARROW` comment in `hooks/pre-publish-guard.js`: literal paths, `-m` messages, an optional `&& git push`) and the repository has no commit hook. Any other line, a `git config` failure, a hook (`core.hooksPath`, `hook.*` config, a hook file or an unreadable hooks folder), a control character in the command, a `git` failure on an added path, or more than one `EOF` line scans the whole tree as before, and the ask then ends with `(scanned the whole tree: <reason>)`. Known gaps, in the narrowed and the wide scan alike: an untracked symlink is read through its target; `CDPATH` and bash's physical-path `cd` fallback can lead the shell to another folder than the hook resolves; clean/smudge filters can change what `git add` stages; the wide scan skips ignored files that `git add -f` stages and reads the working tree, not the index (the push check still reads it). The licensed-data scanner still reads the working tree after any `git add` (regression tests in `pre-publish-guard.test.js`).
- `evolv-destructive-guard.js` no longer blocks text that is only posted: the body or title of `gh pr|issue|release|gist|discussion` (for example `gh pr create --body "… how the guard handles rm -rf / …"`) is treated like a commit message. A `$(…)` or backtick substitution inside that text still runs and is still checked, also inside `$'…'` strings and unquoted heredocs, with a relative path in a substitution treated as unresolved. `VAR=x gh …` is not exempt. Real deletes are still denied (regression tests in `evolv-destructive-guard.test.js`).
- `learn-as-you-build`: a checkpoint no longer loses answered questions. The picks lived only in the widget's memory, and one `Send results` message at the end was the only thing sent, so a re-render or an app reload lost every answer. Now the session writes every item (ids R1, Q1, E1) to `.learning/milestones/NN-checkpoint.md` before it delivers the checkpoint, in every folder, with the answer key at the end and no grader's notes. When it creates `.learning/`, it writes `.learning/.gitignore` with the single line `*`, which keeps the folder out of git before or after `git init`, in a git worktree, and with no git command. A shared repo is defined as a repo that other people also push to. In a shared repo, `LEARNING_LOG.md` goes into the exclude file at the path that `git rev-parse --git-path info/exclude` prints, and the folder of that path is created if it is missing. The widget is used only when it can send a line to the chat; otherwise the checkpoint runs in markdown. The widget sends one `ANSWER` line, with the milestone and the attempt number, for each pick, skip, or Save of an explain-it-back answer; it turns each newline in a text into ` / `. Skip locks the question, like a pick. The markdown format records each letter before it explains. The session records each answer in the file at once and judges right or wrong from the file's answer key. The first recorded pick or skip stands; a repeat leaves the row as it is and gets a one-line reply. `Send results` still starts grading: it fills rows that have no answer, a non-empty text in it that differs replaces a saved explain-it-back text, and each text sits between `<<<E1` and `>>>`. If items are still unanswered, the session lists them and grades only when the user says yes. A results message that arrives during urgent work is recorded at once and graded after the urgent work. The `Graded:` line under `Attempt:` at the top of the file records when the current attempt was graded. A lite checkpoint with no explain-it-back items closes when every item that is not retired has an answer; one with explain-it-back items stays open until a results message arrives. "continue" before the results makes the checkpoint owed, without blocking. A new session, a lost widget, or "resume the quiz" reuses the same items; an item is marked `retired` when a code change makes its right option wrong or removes the code it asks about, except in a queued checkpoint, which is pinned to its commit (see Added). "Restart the quiz" keeps the old rows under `Earlier attempts`, keeps retired items retired, and starts a new attempt. A re-ask clears its topic only if it had no recorded pick or skip in an earlier attempt, and the log takes its totals from the first graded attempt, counting each item by its earliest recorded pick or skip. `LEARNING_LOG.md` gains a Re-asks column, shows `in progress, N of M answered` for an open checkpoint (`queued, N of M answered` for a queued one), and is brought up to date from the file at set points, not on every answer. A checkpoint that has a file records its answers there in every mode, `off` too, and the first log update after `off` mode copies every checkpoint file whose cell does not read `done`. In `off` mode, a catch-up with no file uses the conversation as the record.
