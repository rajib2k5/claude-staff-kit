## [Unreleased]

### Added
- `snowflake-sql` skill: a stdlib-only Snowflake SQL API client (`sf.py`, with `test_sf.py`) that authenticates with a PAT, is read-only by default, and refuses destructive SQL without `--destructive`. Its `config.json` is per machine and gitignored; copy `config.example.json`. The kit now has 37 skills.
- `third-party/skills/graphify`: the graphify 0.9.93 skill (Apache-2.0, with its LICENSE and NOTICE). Not installed by `scripts/install.sh`.
- `learn-as-you-build`: a fifth mode, `queued`, for a user who runs several projects or sessions at once, or wants the full quiz without blocking the build. In `full` mode, each session paused at every milestone until the user said "continue", so every build waited on one quiz at a time. In `queued` mode, the session writes the full checkpoint (re-asks, lesson-and-question pairs, 5 to 8 explain-it-back questions) after the commit that finishes the milestone, delivers it, brings the log up to date, and starts the next milestone at once, in the same turn. Several checkpoints can be open at once. An open queued checkpoint is not owed: the log lists it as `queued, N of M answered`, on a new queued list that says how to resume it. An answer line or a results message goes to the checkpoint file of the milestone it names. An answer is recorded with a one-line reply in the widget, or with the explanation of every option in markdown, and the build goes on as it was; results are graded at once, on the strongest model, and only urgent work delays the grading. In markdown, every unanswered item goes out in one message, a reply that names no item gets `Which item?` before it is recorded, and a reply that names no milestone, while several checkpoints are open, gets `Which milestone?`. The widget's fixed header line, the `Recorded` reply, and a "Grade now?" ask with several checkpoints open name the milestone. Re-asks come from the missed topics in the log when the checkpoint file is written, and a topic that an open checkpoint already re-asks is not chosen again while that re-ask has no answer. A `Code at:` line pins each queued checkpoint to its milestone commit, on a branch that is kept, such as a pushed `main`. With no such commit, the session copies every file that the milestone added or changed to `.learning/milestones/NN-code/`, not only the cited ones, and the line names the copies. The line has no period after the sha. The widget header, and each lesson of a checkpoint written in `queued` mode, say that the items describe the code at that commit, its citations are not refreshed, a later milestone does not retire its items, and its explain-it-back answers are graded against that commit, with each `file:line` labelled with the pin. A resume with several open checkpoints lists each one with its N of M, and the build goes on while the session waits for the pick. In `queued` mode, every open checkpoint that is not owed is queued, also one paused in `full` mode or written before the switch. One with no `Code at:` line gets the last commit of its milestone at once, and only a pin in its widget header. If that commit is on no kept branch, the milestone's files are copied from it with `git show <sha>:<path>`. If the commit is not clear, the session asks in one line, keeps building, and does not grade that checkpoint until the answer. On a switch to `full`, the next milestone pauses and open queued checkpoints stay queued; on a switch to `lite` or `deferred`, they become owed; on a switch to `off`, they and their log entries stay as they are. A restarted queued checkpoint reads `queued, attempt 2, N of M answered`. The less intrusive order is now `off`, `deferred`, `lite`, `queued`, `full`. The token-economy rule now limits the recording of an answer, not the whole turn, so the work goes on after the reply.

### Changed
- `data-cost`, `data-snowflake-audit`, `data-snowflake-tune`, the `snowflake-architect` agent and the `/sf-audit` and `/sf-tune` commands now say to run queries through `snowflake-sql` when the Snowflake MCP server is unavailable.

### Fixed
- `learn-as-you-build`: a checkpoint no longer loses answered questions. The picks lived only in the widget's memory, and one `Send results` message at the end was the only thing sent, so a re-render or an app reload lost every answer. Now the session writes every item (ids R1, Q1, E1) to `.learning/milestones/NN-checkpoint.md` before it delivers the checkpoint, in every folder, with the answer key at the end and no grader's notes. When it creates `.learning/`, it writes `.learning/.gitignore` with the single line `*`, which keeps the folder out of git before or after `git init`, in a git worktree, and with no git command. A shared repo is defined as a repo that other people also push to. In a shared repo, `LEARNING_LOG.md` goes into the exclude file at the path that `git rev-parse --git-path info/exclude` prints, and the folder of that path is created if it is missing. The widget is used only when it can send a line to the chat; otherwise the checkpoint runs in markdown. The widget sends one `ANSWER` line, with the milestone and the attempt number, for each pick, skip, or Save of an explain-it-back answer; it turns each newline in a text into ` / `. Skip locks the question, like a pick. The markdown format records each letter before it explains. The session records each answer in the file at once and judges right or wrong from the file's answer key. The first recorded pick or skip stands; a repeat leaves the row as it is and gets a one-line reply. `Send results` still starts grading: it fills rows that have no answer, a non-empty text in it that differs replaces a saved explain-it-back text, and each text sits between `<<<E1` and `>>>`. If items are still unanswered, the session lists them and grades only when the user says yes. A results message that arrives during urgent work is recorded at once and graded after the urgent work. The `Graded:` line under `Attempt:` at the top of the file records when the current attempt was graded. A lite checkpoint with no explain-it-back items closes when every item that is not retired has an answer; one with explain-it-back items stays open until a results message arrives. "continue" before the results makes the checkpoint owed, without blocking. A new session, a lost widget, or "resume the quiz" reuses the same items; an item is marked `retired` when a code change makes its right option wrong or removes the code it asks about, except in a queued checkpoint, which is pinned to its commit (see Added). "Restart the quiz" keeps the old rows under `Earlier attempts`, keeps retired items retired, and starts a new attempt. A re-ask clears its topic only if it had no recorded pick or skip in an earlier attempt, and the log takes its totals from the first graded attempt, counting each item by its earliest recorded pick or skip. `LEARNING_LOG.md` gains a Re-asks column, shows `in progress, N of M answered` for an open checkpoint (`queued, N of M answered` for a queued one), and is brought up to date from the file at set points, not on every answer. A checkpoint that has a file records its answers there in every mode, `off` too, and the first log update after `off` mode copies every checkpoint file whose cell does not read `done`. In `off` mode, a catch-up with no file uses the conversation as the record.

## [1.1.0] - 2026-10-28

### Added
- 10 `claude-*` skills that close gaps found by mapping the four Anthropic certification blueprints (CCAR-F, CCAR-P, CCAO-F, CCDV-F) against every installed skill: `claude-agent-orchestration`, `claude-context-management`, `claude-prompt-engineering`, `claude-evals`, `claude-api-ops`, `claude-rag-and-citations`, `claude-code-config`, `claude-tool-and-mcp-design`, `claude-governance`, `claude-solution-design`. Written for model generation 5 and later; every identifier is sourced to current docs.
- `docs/skill-gap-2026-10/`: the study that produced them (concept tags, coverage map, graphify graph, evidence-gated validation ledger and channel reports). Raw third-party text is not committed.
- `learn-as-you-build` skill: teaches the user the code while it is built. It builds one milestone, writes a walkthrough doc and concept notes, then runs a checkpoint of lessons, each followed by its own quiz question with every option explained, and 5 to 8 explain-it-back questions. Four modes (`full`, `lite`, `deferred`, `off`) with switch phrases and a per-project default let a user on a deadline bypass it. It uses an inline widget when the host has one and plain markdown otherwise.

### Changed
- `rules/agent-models.md`, `skills/cost-conscious-orchestration`: model table moved to the 5.5 generation (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-fable-5-1`, `claude-haiku-5-5`); notes that Claude Code needs v2.1.293+ for Haiku 5.5.

### Earlier (unreleased before 1.1.0)
- `third-party/`: vendored `threejs` 1.0.0, `cert-safari-quiz` 0.1.0, `evolv-taste-pilot` 0.1.0 plugins and the `code-mods-essentials` skill, with provenance in `third-party/README.md`. The three plugins are listed in the marketplace. The `staff-kit` plugin itself is unchanged.

## [1.0.0] - 2026-10-11

### Added
- First packaged release of the `~/.claude` engineering library as a Claude Code plugin and as a dotfiles install.
- 25 skills: 13 `staff-*` engineering workflows, 8 `data-*` data-platform workflows, `cost-conscious-orchestration`, `destructive-ops-guard`, `evidence-gated-validation`, `simple-english`.
- 19 agents, each with an explicit `model:` (adversarial validator pinned to Opus).
- 12 slash commands (`/bootstrap`, `/ship`, `/validate`, `/deep-review`, `/design`, `/rca`, `/adr`, `/dbt-audit`, `/sf-audit`, `/sf-tune`, `/dq`, `/standards`).
- 19 rule files and the tiered contexts (tier 0 always, tier 1 per role, tier 2 per domain).
- Hooks: PreToolUse destructive-ops guard (121 unit tests), SessionStart and Stop skills enforcer. `hooks/hooks.json` wires them for plugin mode.
- Skills enforcer Stop branch no longer warns on its own policy text (it quotes "tests pass"), and exits quietly when `stop_hook_active` is set. Regression tests in `hooks/evolv-skills-enforcer.test.js`.
- Plugin mode: the skills enforcer now prints the kit root when `CLAUDE_PLUGIN_ROOT` is set, so `~/.claude/rules/...` references in skills and agents resolve under the plugin.
- `scripts/install.sh` (link or copy into `~/.claude`, never overwrites without `--force`, backs up first), `scripts/merge-settings.py` (idempotent hook registration with backup), `scripts/install-plugins.sh` (curated marketplace plugins), `scripts/validate.sh` (manifests, frontmatter, hook tests).
- Cortex CLI adapter (`adapters/cortex/`): symlink layout and the bootstrap script that seeds `cortex ctx`.
- Global memory seed (`memory/`) and the global `CLAUDE.md` template (`templates/global-CLAUDE.md`), both opt-in at install.
- Docs: component inventory with what was excluded and why, marketplace comparison, recommended plugins.
